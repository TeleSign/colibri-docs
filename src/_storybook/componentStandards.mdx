## 1. Component Naming

**Purpose:** Ensure all components follow a **consistent and descriptive naming convention**, making them easier to discover, use, and maintain.

### Guidelines

- Use **PascalCase** for all component names.  
  Example:
  ```text
  ColModalHeader, ColGridItem, ColModalFooter
  ```
- Names should **clearly describe the component’s purpose**.  
  Avoid vague names like `Box` or `Container` unless their role is truly generic.

- For related or grouped components, use **compound names** that reflect hierarchy or context:
  Example:
  ```text
  ColModalHeader, ColModalFooter, ColGridItem
  ```

### Notes / Tips

- Always check if a name is **already used** in the library to avoid conflicts.  

### Rationale

- Compound names make **relationships between components explicit**.  
- Consistent naming improves **discoverability**, **readability**, and reduces **developer confusion** across the component library.

## 2. Property (Prop) Naming

**Purpose:** Ensure props are named consistently and clearly, making components easier to use and understand.

### Guidelines

- Use **camelCase** for prop names.
- **Boolean props** should be named to reflect true/false nature and should start with **is** or **has**.
- **Event handler props** should start with **on** and describe the action.
- **Data or value props** should be descriptive and concise.
- Avoid abbreviations unless they are widely recognized.

### Notes / Tips

- When adding a new prop, ask: *“Will another developer understand this prop’s purpose without extra documentation?”*  
- Prefix boolean props with `is` or `has` to indicate a **true/false** value.
- For event handlers, always start with `on` and be specific: `onClick`, `onFormSubmit`, not `handleEvent`.

### Examples

- **Boolean props:**
  - Good: `isVisible`, `hasError`, `isLoading`
  - Bad: `visibleFlag`, `errorStatus`

- **Event handlers:**
  - Good: `onClick`, `onSubmit`, `onFormReset`
  - Bad: `handleEvent`, `doAction`

- **Data/value props:**
  - Good: `user`, `items`, `selectedValue`
  - Bad: `usr`, `val`, `dataObj`

**Rationale:**
- Consistent camelCase naming aligns with JavaScript conventions.
- Boolean props clearly indicate their purpose and expected values.
- Descriptive prop names improve code readability and reduce confusion.

# 3. State Naming

**Purpose:** Maintain clear and predictable names for component state to improve readability and maintainability.

## Guidelines

- Use **camelCase** for state variable names.
- Boolean state variables should start with **is** or **has**.
- Use descriptive names that clearly indicate what the state represents.
- Avoid vague names like `data` or `temp` unless the context is obvious.

### Examples

- **Boolean state:**
  - Good: `isOpen`, `hasError`, `isActive`
  - Bad: `openFlag`, `errorStatus`

- **Other state variables:**
  - Good: `currentPage`, `formValues`, `selectedItem`
  - Bad: `data`, `tempValue`
  
**Rationale:**
- Consistent camelCase matches JavaScript and React conventions.
- Prefixing boolean state with `is/has` immediately indicates a true/false flag.
- Descriptive names improve readability and reduce confusion for developers working on the component.

# 4. Event Naming

**Purpose:** Ensure event names are clear, predictable, and easy to understand for anyone using or extending the component.

## Guidelines

- Use **camelCase** for event names.
- Prefix event handlers with **on** to indicate they are events.
- Use descriptive names that clearly indicate what action triggers the event.
- Avoid generic names like `handleEvent` or `doAction`.

### Examples

- **Good:** `onClick`, `onChange`, `onSubmit`, `onFormReset`
- **Bad:** `handleEvent`, `doAction`

**Rationale:**
- The `on` prefix is standard in React and helps differentiate events from regular functions.
- Descriptive names make it clear what the event represents and when it is fired.
- Consistent naming improves maintainability and developer experience when using the component library.

# 5. Slot Naming

**Purpose:** Ensure slots are named consistently so consumers of the component understand their purpose and usage quickly.

## Guidelines

- Use **descriptive, camelCase names** for slots.
- Avoid vague names like `slot1`, `slot2`.
- Keep names short but meaningful, reflecting the content or role of the slot.

### Examples

- **Good:** `header`, `footer`, `content`, `sidebar`, `actions`
- **Bad:** `slot1`, `slot2`, `partA`

**Rationale:**
- Clear slot names improve readability and make it easier for developers to compose components.
- Consistency reduces confusion when multiple components share a similar slot structure.

# 6. CSS Class Naming

**Purpose:** Maintain consistent and predictable CSS class naming conventions to ensure styles are easy to understand, override, and maintain.

## Guidelines

- Use **kebab-case** (lowercase words separated by hyphens) for all CSS class names.
- Class names should be semantic and describe their purpose or role, not their visual appearance.
- When using **BEM (Block Element Modifier)** style, follow the structure:
  `block__element--modifier`.

### Examples

- **Kebab-case:** `input-group`, `toast-content`
- **Semantic:** `input-container`, `error-message`
- **BEM style:** `button__icon--disabled`

**Rationale:**
- Kebab-case ensures class names remain readable and consistent with standard CSS conventions.
- Semantic naming makes components easier to understand and maintain.
- BEM-style naming helps organize related styles and prevents class name collisions

# 7. Component Architecture and Inheritance Layers

**Purpose:**  
Define when to extend from base classes to keep components consistent and predictable.

---

### Base Layers

| Base Class | Use When... | Example |
|------------|------------|---------|
| **ThemedComponent** | Base for all components. Provides theming, design tokens, and shared visual behavior. | ColToast |
| **FormComponent** | The component manages a `value`, handles selection, or interacts with form-like logic. | ColListMenuItem |
| **SelectableFormComponent** | The component can be selected or toggled. | ColToggle, ColCheckboxCard |
| **InputFormComponent** | The component is input with validation, placeholder, etc. | ColTextArea |
| **TextInputBase** | The component handles text-based input behavior (pattern validation, char count, clear button, dirty state). | ColNumberField |
| **AlertComponent** | Use this for components that **display messages or notifications**, with support for **variant, optional title/content/actions, automatic or manual dismissal, and accessible attributes**. | ColBanner |

### Avoid Extending Higher Layers When Not Needed

- Do **not** extend `InputFormComponent` if your component doesn’t require validation or labels.  
- Do **not** use `FormComponent` for components that don’t interact with forms

---

### Guidelines

- **All components must extend `ThemedComponent`** — this ensures theming, token access, and shared visual consistency.  
- Use **FormComponent** for components that manage form-like behavior, including selection and values.  
- Use **SelectableFormComponent** for components that represent selectable/toggleable states.  
- Use **InputFormComponent** for inputs that need validation, placeholder, etc.  
- Use **TextInputBase** for text-based input fields that share logic for clearing, validation, and character counting.  Use **AlertComponent** for components that **display messages or notifications**, supporting **variant, optional title/content/actions, automatic or manual dismissal, and accessibility attributes**.  
 

**Rationale:**  
This layered inheritance model keeps components modular and predictable, ensuring that theming, form behavior, and validation logic remain centralized and reusable.

## When to Create a New Base Layer

Create a new base (or higher-level) component **only when multiple components need to share the same logic or lifecycle behavior**.  
Typical cases include:

- **Theming and design tokens** (e.g., `ThemedComponent`)  
- **Form behavior** — value handling, validation, or association (e.g., `FormComponent`)  
- **Selection or toggling logic** (e.g., `SelectableFormComponent`)  
- **Reusable input patterns** — labels, placeholders, helper text  
- **Shared accessibility or event patterns**

## How to Create a New Base Layer

### 1. Extend the Right Abstraction
Always start from the **lowest suitable base**:
- Use `ThemedComponent` for token or style management.
- Use `FormComponent` for form fields or inputs.
- Use `SelectableFormComponent` or `InputFormComponent` for specialized behavior.

---

### 2. Keep It Abstract and Focused
A base layer should not render templates or be registered as a custom element.  
Its purpose is to encapsulate logic that **child components can inherit** — such as property syncing, event dispatching, or lifecycle hooks.  
Keep responsibilities narrow and reusable; don’t include component-specific logic.

---

### 3. Define a Clear Responsibility and Scope
Each base component should serve a **single, well-defined purpose**:
- `ThemedComponent`: theming, CSS tokens, slot detection.  
- `FormComponent`: value management and form association.  
- `InputFormComponent`: input validation and text-handling.  
- `AlertComponent`: standardized notification structure.  

---

### 4. Use Consistent Naming
Follow the naming convention:
- Use **PascalCase**.
- Choose names that reflect behavior, not appearance.  
  Examples: `FormComponent`, `SelectableFormComponent`, `AlertComponent`.

Avoid generic terms like `BaseComponent` unless it’s truly generic.

---

### 5. Document the Layer
Every new base class should include a short **documentation block** explaining:
- Its **purpose** (what it provides and why it exists).
- Any **required properties or expected behavior**.

This helps maintain consistency and ensures new developers understand the hierarchy.

# 8. Quick Reference / Summary

This section summarizes the main naming and structural standards for creating components in the library.

---

### Component Standards Overview

| Category | Convention | Tip | Example |
|----------|-------------|-----|---------|
| **Component Names** | PascalCase | Must be unique and descriptive | ColButton, ColSelect, ColToast |
| **Props** | camelCase | Keep names clear and intuitive | isDisabled, userName, onSubmit |
| **Boolean Props** | camelCase | Prefix with `is` or `has` | isOpen, hasError, isVisible |
| **Events** | camelCase | Start with `on` + action | onChange, onClick, onDismiss |
| **State Variables** | camelCase | Reflects purpose or state meaning | isLoading, selectedItem, currentPage |
| **Slots** | lowercase | Use short, descriptive names | header, footer, actions, icon |
| **CSS Parts** | lowercase, hyphen-separated | Match DOM structure | part="toast", part="content" |
| **CSS Classes** | kebab-case | Semantic, not visual | .toast-content, .button-primary |
| **Base Class** | PascalCase | Extend by functionality | ThemedComponent, FormComponent, InputFormComponent |

---

### Base Class Quick Guide

| Use Case | Extend | Tip | Example |
|--------------------|----------------------|-----|---------|
| Theming, tokens, or shared styles | **ThemedComponent** | Foundation for all components | ColToast, ColButton |
| Value handling, selection, or form logic | **FormComponent** | Handles values, syncs with forms | ColListMenuItem |
| Selection behavior | **SelectableFormComponent** | Adds toggle/checked support | ColToggle, ColCheckboxCard |
| Validation, helper text, or input behavior | **InputFormComponent** | Ideal for validated inputs | ColTextArea |
| Text-based input logic | **TextInputBase** | Manages typing, char count, and clear button | ColNumberField |
| Notification display | **AlertComponent** | Handles variants, title/content, and dismissal | ColBanner |
